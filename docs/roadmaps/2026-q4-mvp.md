# MVP build & pilot (6 weeks)

Six weeks is a planning target for a narrow MVP, not a guarantee — it depends on available hours and reuse.
Dates assume a start on **Mon 19 Oct 2026**; shift the table if that changes.

| Week | Dates | Focus | Deliverables | Features |
|---|---|---|---|---|
| 1 | 19–25 Oct | Workflow & prototypes | Resolve open questions in specs → `ready`; accept/reject ADR-0006, 0008, 0009; choose DB (ADR-0002); scaffold Laravel + Inertia + Vue + Tailwind on Herd; CI; test screens with target users | — |
| 2–3 | 26 Oct – 8 Nov | Core product | Auth, tenant isolation, trips/departures, public pages, booking creation, capacity controls, dashboard | F-009, F-001, F-003, F-002, F-005, F-004, F-007 |
| 4 | 9–15 Nov | Operational workflow | Payment records, seller instructions, confirmations, cancellation handling, admin/support view | F-006, F-008, F-007, F-010–F-015 |
| 5 | 16–22 Nov | Pilot | Onboard a small group of operators; observe real usage; no speculative features | — |
| 6 | 23–29 Nov | Hardening & decision | Security checks, backup restore test, mobile usability, booking reliability, support burden → continue/pivot | F-009 |

## Success metrics (blueprint §9)

| Metric | Target |
|---|---|
| Time to first published trip | < 10 minutes |
| Independent onboarding | Most pilot sellers finish setup without help |
| Routine edit speed | Price/capacity update < 30 s |
| First real booking | Within 14 days for active pilot sellers |
| Repeat use | Sellers return to manage another departure/booking |
| Booking reliability | Zero overbooking or cross-seller exposure |
| Willingness to pay | Some active sellers commit to a paid plan |
| Support burden | Declining over the pilot |
